# Staging-equivalent proof harness for ClassroomPath #162

> Status: implementation complete / operational proof pending
> Current gate: **K NOT READY**
> Scope: repository-owned preparation for a future staging-only operational test

This runbook describes the isolated host and the commands that will be used for
K. It is deliberately not a record that K has run. No production authority,
production host, production environment, tag, release, or GitHub variable is
used by this harness.

## Why normal staging is excluded

The normal staging host uses the `classroompath-staging` Compose project while
the production executor and recovery path use `classroompath-production`.
Because this Compose file has fixed container names and named persistent
volumes, running the production executor against normal staging can stop the
old containers and start the new release against a different volume namespace.
That would not prove rollback of the state that the previous release actually
served.

K therefore requires a separate host, Docker daemon, filesystem, database,
credentials, and test URL. Inside that isolated host the Compose project name
must remain exactly `classroompath-production`; isolation is provided by the
host boundary, not by a test-only Compose override.

## Repository entrypoint and safety fence

The implementation is [`scripts/staging-equivalent-harness.sh`](../../scripts/staging-equivalent-harness.sh).
It has two classes of commands:

- Read-only/local-evidence commands: `validate-environment`, `validate-host-path`,
  `attest-p`, `validate-attestation`, `prepare-recovery`, `validate-recovery`,
  `validate-migration`, `validate-transition`, and `evidence`.
- Isolated-host mutation commands: `provision`, `fault-leg`, `success-leg`, and
  `rollback`.

The mutation commands require both `--confirm-staging-equivalent` and a
durable identity marker. The fence rejects the command unless all of these
identities agree:

```text
K_ENVIRONMENT=staging-equivalent
K_PRODUCTION_TARGET=false
K_COMPOSE_PROJECT=classroompath-production
K_NORMAL_STAGING_ALLOWED=false
K_RECOVERY_AUTHORITY_SCOPE=local-staging-equivalent
K_DATABASE_SCOPE=staging-equivalent
K_CREDENTIALS_SCOPE=staging-equivalent
K_DATABASE_ENDPOINT_SHA256=<sha256-of-private-staging-database-url>
host machine-id hash == durable marker hash
deploy-root canonical-path hash == durable marker hash
Docker daemon ID == durable marker ID
/srv/classroompath/downloads filesystem-device hash == durable marker hash
test URL hash == durable marker hash
```

The Docker daemon and filesystem checks are performed again by the host
contract before a mutation. A DNS name containing `staging` is not an identity
factor and cannot authorize the command. The harness never reads
`PRODUCTION_RECOVERY_SHA` from GitHub; recovery identity is supplied through
the local K contract.

## Required host admission

The host administrator must create the marker and an operator-managed config
outside the deploy root. The marker is not generated by a deploy checkout and
must contain, at minimum:

```text
STAGING_EQUIVALENT_VERSION=1
STAGING_EQUIVALENT_ID=<opaque-host-id>
STAGING_EQUIVALENT_PRODUCTION_TARGET=false
STAGING_EQUIVALENT_HOST_ID_SHA256=<sha256-of-host-machine-id>
STAGING_EQUIVALENT_DEPLOY_ROOT_SHA256=<sha256-of-canonical-deploy-root>
STAGING_EQUIVALENT_COMPOSE_PROJECT=classroompath-production
STAGING_EQUIVALENT_NORMAL_STAGING_ALLOWED=false
STAGING_EQUIVALENT_RECOVERY_AUTHORITY_SCOPE=local-staging-equivalent
STAGING_EQUIVALENT_DATABASE_IDENTITY=<opaque-isolated-database-id>
STAGING_EQUIVALENT_DATABASE_ENDPOINT_SHA256=<sha256-of-private-staging-database-url>
STAGING_EQUIVALENT_DATABASE_SCOPE=staging-equivalent
STAGING_EQUIVALENT_CREDENTIALS_SCOPE=staging-equivalent
STAGING_EQUIVALENT_DOCKER_DAEMON_ID=<docker-info-id>
STAGING_EQUIVALENT_GATEWAY_DOWNLOAD_DEVICE_SHA256=<sha256-of-df-device>
STAGING_EQUIVALENT_BASE_URL_SHA256=<sha256-of-test-base-url>
```

The values are collected on the isolated host, for example with
`docker info --format '{{.ID}}'`, `df -P /srv/classroompath/downloads`, and
`sha256sum`. The marker and config are mode `0600`; neither contains service
secrets. `K_DATABASE_IDENTITY` is a non-secret identifier for the isolated
database and must match the durable marker; the database endpoint and
credentials themselves remain in the private runtime file.

The host must provide the existing production host contract: Bash/POSIX,
Git, Docker, Docker Compose, curl, tar, base64, sha256sum, and the standard
utilities declared by `scripts/lib/production-host-contract.sh`. The effective
executor `PATH` is rebuilt from that allow-list. `node` and `npm` are excluded;
Node is used only inside the exact verifier image. The host administrator must
not install Node/npm to satisfy K.

The deploy root is private and must contain no unrelated checkout or operator
files. A non-clean checkout is rejected; the harness never invokes `git clean`.
The protected file
`config/.env.bak-billingfix-20260623` is not read, copied, moved, or deleted.
Its presence in a checkout is an immediate fail-closed condition. It is not a
valid reason to weaken cleanup on the K host.

## Input contract

The K config is a plain file containing only `K_*` assignments. It is parsed,
not sourced, and secret-shaped key names are rejected. The operator must bind
the following to exact, current artifacts before using the legs:

```text
P = K_P_APP_SHA                 previous ClassroomPath commit
C = K_C_APP_SHA                 candidate ClassroomPath commit
R = K_RECOVERY_SHA              independently approved recovery commit
K_CANDIDATE_SHA                 exact C SHA repeated in the transaction payload/state

K_P_RELEASE_ID                  exact P Release Bundle releaseId
K_C_RELEASE_ID                  exact C Release Bundle releaseId
K_P_BUNDLE_FILE / K_C_BUNDLE_FILE  external immutable artifact files
K_P_CONTRACT_FILE / K_C_CONTRACT_FILE  external immutable artifact files
K_P_*_IMAGE and K_C_*_IMAGE     every runtime image, each with @sha256:...
K_P_RC_RUN_ID / K_C_RC_RUN_ID  exact release-candidate run IDs
K_P_OPENPATH_SHA / K_C_OPENPATH_SHA
K_P_BUNDLE_SHA256 / K_C_BUNDLE_SHA256
K_P_CONTRACT_SHA256 / K_C_CONTRACT_SHA256
K_C_PAYLOAD_FILE                exact C deploy payload
K_C_SOURCE_DIR                  clean external checkout at C
K_RECOVERY_SOURCE_DIR           clean external checkout at R
K_RECOVERY_SOURCE_SHA           exactly R
K_RECOVERY_CONTRACT_VERSION
K_RECOVERY_SOURCE_VERSION
K_RECOVERY_ARTIFACT_FILE        external generated artifact path
K_RECOVERY_ARTIFACT_SHA256
K_RECOVERY_EXECUTOR_SHA256
K_RECOVERY_TRANSMITTED_FILE    external byte copy path
K_RECOVERY_PERSISTED_FILE      canonical deploy-root recovery path
K_RECOVERY_WRAPPER_SOURCE_FILE exact wrapper from R
K_RECOVERY_WRAPPER_SHA256
K_DIAGNOSTIC_FALLBACK_FILE     exact fallback from R
K_DIAGNOSTIC_FALLBACK_SHA256
K_RUNTIME_SECRETS_FILE         private external .env with staging credentials
K_DATABASE_IDENTITY            non-secret isolated database identity
K_DATABASE_ENDPOINT_SHA256     hash of the private staging DATABASE_URL value
K_DATABASE_SCOPE               exactly `staging-equivalent`
K_CREDENTIALS_SCOPE            exactly `staging-equivalent`
```

`R` must be a full lowercase 40-character SHA and must differ from `C`.
`P`, `C`, and `R` are resolved from the artifacts and clean exact checkouts
used for this run; values from an old handoff are not authoritative.

`K_RUNTIME_SECRETS_FILE` is an operator-managed private file outside the deploy
root; the operator must protect it with mode `0600`. It is never sourced as
shell code and is never archived as evidence. It must contain exactly one
single-line `GHCR_USERNAME=...` and one
single-line `GHCR_TOKEN=...` assignment and exactly one `DATABASE_URL=...`
assignment; the remainder may be the staging application `.env` contract copied
during provisioning. The harness hashes the database URL in memory and compares
it to `K_DATABASE_ENDPOINT_SHA256` and the durable marker without printing it.
It parses the assignments without sourcing the file. The two registry
credentials are exported only to the short-lived Docker login/forward/recovery
processes. The forward executor receives the following explicit
application-runtime allowlist, with absent optional assignments represented as
empty values:

```text
CP_BILLING_MODE
CP_PLATFORM_ADMIN_EMAILS
CP_CLIENT_CANARY_ADMIN_TOKEN
VAPID_PUBLIC_KEY
VAPID_PRIVATE_KEY
VAPID_CONTACT
STRIPE_SECRET_KEY
STRIPE_WEBHOOK_SECRET
STRIPE_ANNUAL_PRICE_1_10
STRIPE_ANNUAL_PRICE_11_25
STRIPE_ANNUAL_PRICE_26_50
STRIPE_ANNUAL_PRICE_51_100
STRIPE_ONBOARDING_PRICE_1_25
STRIPE_ONBOARDING_PRICE_26_100
STRIPE_PILOT_PRICE
CP_EMAIL_PREFLIGHT_ALLOW_DAILY_QUOTA
```

No other assignment from the secrets file is forwarded. `CP_EMAIL_PREFLIGHT_MODE`
is not read from that file: K supplies the explicit `skip` override while the
production and normal-staging defaults remain unchanged. Runtime secret values
are kept out of stdout/stderr and evidence; the secrets file is never sourced
as shell code or archived.

## Provisioning exact P

Provisioning starts only on the isolated host after the fence has been created.
It uses the production Compose file and the literal project name
`classroompath-production`:

```sh
scripts/staging-equivalent-harness.sh validate-environment --config "$K_CONFIG"
scripts/staging-equivalent-harness.sh provision \
  --config "$K_CONFIG" --confirm-staging-equivalent
```

`provision` is fail-closed and idempotent in the safe case. It refuses a
contradictory durable `current`, refuses pre-existing project containers with
no durable state, refuses pre-existing production-named volumes or network
without a durable P, checks out exact P with its exact OpenPath gitlink, verifies
the P bundle and OpenPath contract through the immutable verifier, requires
digest-pinned images, and uses the immutable migration runner. The order is
deliberately:

```text
validate environment -> exact P checkout/bundle -> assets and immutable image pull
-> P migrations -> compose up P -> readiness -> live attestation
-> persist P bundle -> activate P -> post-activation attestation
```

`run-migrations-docker.sh` runs the migration runner as a one-shot container and
does not require the application containers to be running. Thus no application
runtime is exposed before the database preparation has passed.

Provisioning records its attempt in
`release-state/provision-attempt.env`. The record proves that the fixed
production-named resources were absent before that attempt and records every
container, volume, and network identity created by it. An exit path before
activation performs an ownership-bound cleanup of only those exact identities;
it never uses an unscoped `compose down`. A cleanup failure remains durable as
`CLEANUP_FAILED` and the next `provision` retries that same cleanup after
revalidating the project, service, labels, names, and IDs. If ownership or the
durable state is ambiguous, provisioning fails closed and the operator must
preserve the evidence and use the emergency procedure below.

Before activating durable P it snapshots the live containers and verifies the
runtime without declaring P current. It then persists the exact P Release
Bundle v2 and atomically activates P, followed by a second live attestation.
The command must leave these facts true:

```text
current == P releaseId
checkout HEAD == P.classroomPathSha
HEAD:upstream/openpath == P.openPath.sourceSha
gateway/api/spa/provision images == exact P digest pins
Compose project == classroompath-production
named volumes == classroompath-production_* identities
health == HTTP 200
ready == HTTP 200, valid JSON, ready === true
```

## K0 read-only attestation

K0 is available independently of either leg:

```sh
scripts/staging-equivalent-harness.sh attest-p --config "$K_CONFIG"
```

It writes a bounded `p-attestation.snapshot` but does not stop, recreate, or
mutate application containers. K0 rejects any mismatch in durable P versus
live service identity, including:

- checkout SHA and OpenPath gitlink;
- image reference and actual `RepoDigest` for gateway, API, SPA, and the
  provision service;
- container IDs, fixed names, Compose labels, status, and network;
- `api-data`, installer template, and installer artifact volume IDs, names,
  mountpoints, Compose project labels, and Compose keys;
- every production bind/volume mount, including `/srv/classroompath/downloads`
  and `spa-nginx.conf`;
- the verifier runtime projection, health, and semantic readiness.

The baseline snapshot is retained. A later rollback attestation must compare
all persistent volume and mount identities to that baseline, not only to the
P Release Bundle.

## Recovery preparation and readiness

Recovery is prepared from the exact clean R checkout once:

```sh
scripts/staging-equivalent-harness.sh prepare-recovery --config "$K_CONFIG"
```

This runs the R authority package/preflight flow, hashes the archive and the
embedded executor, and refuses to overwrite an existing artifact or source
identity. The operator then records the generated, non-secret values from
`recovery-source-identity.env` into the K config, including the exact
`K_RECOVERY_ARTIFACT_SHA256` and `K_RECOVERY_EXECUTOR_SHA256`. The config must
also set the canonical persisted path:

```text
<deploy-root>/recovery/releases/<K_RECOVERY_ARTIFACT_SHA256>/production-recovery-bundle.tgz
```

The fault and success legs preflight the exact extracted R executor against
the durable P `previous` bundle before the mutation boundary. The readiness
proof must show that R can load and validate P, validate the contract and
digest-pinned images, materialize its runtime, construct the rollback plan,
and run its preflight entrypoint without candidate helpers or host Node/npm.

At the forward boundary the exact bytes are transmitted, persisted by the
production recovery artifact lifecycle, and recorded in both
`current-artifact.env` and the transaction marker. The harness checks:

```text
generated R archive == transmitted bytes
transmitted bytes == persisted bytes
persisted archive hash == recovery identity hash
persisted executor hash == recovery identity hash
transaction recovery path/hash/source == the same identity
```

No checkout or repack of R is permitted after a failure.

## Mutation boundary and transaction evidence

The harness preserves the production boundary at the existing
`deployment_transaction_transition SWITCHING SWITCH` call inside the migration
path. The expected forward timeline is:

```text
PREPARED -> SWITCHING -> ACTIVATED_UNVERIFIED -> VERIFIED -> COMMITTED
```

The candidate cannot become `current` before verification and commit. The
failure timeline is:

```text
PREPARED -> SWITCHING -> ACTIVATED_UNVERIFIED -> FAILED
       -> ROLLING_BACK -> ROLLED_BACK
```

Forward phases are recorded through the transaction history hook. Because the
recovery authority is independently pinned, the harness also observes the
rollback state file externally and requires the exact `ROLLING_BACK` and
`ROLLED_BACK` observations before claiming a successful rollback. Missing or
ambiguous phase evidence fails closed.

Every forward attempt has a fresh durable
`DEPLOYMENT_TRANSACTION_ID`. The harness classifies the result by rereading
`release-state/deployment-phase.env`, including the phase, boundary,
candidate, previous release, and transaction ID. A forward error before
`MUTATION_BOUNDARY_REACHED=1` fails without rollback. Any forward, observer,
diagnostic, history, or evidence error after the boundary uses the exact
persisted R recovery artifact unless the durable state strongly proves the
intended terminal state. A `COMMITTED` result is terminal only for the normal
success leg; a fault leg that reaches `COMMITTED` is a failed rehearsal and
must recover to P.

The leg records two independent results:

```text
SAFETY_OUTCOME=COMMITTED | ROLLED_BACK | NO_RECOVERY | RECOVERY_FAILED
EVIDENCE_OUTCOME=COMPLETE | INCOMPLETE
```

Evidence is best-effort before and after recovery. An incomplete bundle never
suppresses an already-required recovery: `EVIDENCE_OUTCOME=INCOMPLETE` makes K
fail while the host may still be safely at P. If the transaction state is
unreadable or does not match the current attempt, the harness still invokes
the persisted R path in post-forward mode; it reports `ROLLED_BACK` only after
the durable state proves `ROLLED_BACK` with `current == P`. A recovery command
that returns without that proof is `RECOVERY_FAILED` and requires the emergency
procedure.

## Fault leg (staging-equivalent only)

The controlled fault is not run by this implementation change. When separately
authorized, the future command is:

```sh
scripts/staging-equivalent-harness.sh fault-leg \
  --config "$K_CONFIG" --confirm-staging-equivalent
```

The watchdog captures the baseline P gateway ID, waits for the exact durable
transaction's `PREPARED` state, then waits for that same transaction's
`ACTIVATED_UNVERIFIED` phase, queries containers by both labels
`com.docker.compose.project=classroompath-production` and
`com.docker.compose.service=gateway`, and requires a single running candidate
ID whose ID differs from P and whose image is the exact C gateway digest. Only
then does it execute `docker stop <candidate-id>`, once. It never selects the
target by fixed `container_name` alone and cannot stop P.

Stale `COMMITTED`, `ROLLED_BACK`, or other terminal state from an earlier
attempt cannot arm the watchdog: it must observe the current transaction ID,
candidate release/SHA, and `PREPARED` after the watchdog starts. If the
watchdog fails after the current transaction crossed the boundary, the shared
post-forward safety path recovers. If the forward accidentally reaches
`COMMITTED` during a fault leg, the leg still fails and the same path restores
P before any PASS decision.

The leg must prove candidate failure, boundary reach, bounded diagnostic
collection, exact recovery identity, successful R rollback, and a post-rollback
K0 against the original persistent-volume baseline. Recovery is attempted
before strict diagnostic, transaction-history, fault-target, or evidence-bundle
validation. The candidate diagnostic is kept when valid; the independent R
fallback is used only for missing, failed, stale, or contradictory candidate
output. A pre-existing diagnostic artifact is rejected so a retry cannot reuse
stale evidence; both candidate and fallback output are scanned for secret-shaped
content and bounded before archiving.

The success leg follows the same policy. Any non-zero forward result after the
boundary—including a command error after durable `COMMITTED`—is a failed leg,
but it first attempts exact-R recovery and requires P to be restored. An error
in `SWITCHING`, `ACTIVATED_UNVERIFIED`, `VERIFIED`, or an unreadable/ambiguous
state is therefore never left at C. Recovery success is recorded as
`SAFETY_OUTCOME=ROLLED_BACK`; it never changes that leg into a success.

## Rollback and emergency procedure

The normal fault leg invokes the stable wrapper and transmits the already
persisted archive. The wrapper executes only the R artifact's
`production-recovery-executor.sh` and its bundled `rollback-executor.sh`; it
does not source executable helpers from the C checkout.

If that automated attempt fails on the isolated host:

1. Preserve the entire evidence directory and do not run `git clean`, edit the
   checkout, replace the recovery archive, or change the recovery identity.
2. Re-run the fence read-only and inspect `deployment-phase.env`. A boundary
   value of `0` means the runtime rollback path is not authorized. A phase of
   `ROLLING_BACK` means the original process must be observed to exit before a
   retry. A durable `ROLLED_BACK` with `current == previous` is already safe
   and the manual command is a no-op. Otherwise the manual command accepts only
   a boundary of `1`, an allowed in-flight/failed phase, the exact persisted R
   identity, and `previous == P`; it does not depend on candidate helpers or
   transaction history.
3. Validate the persisted archive and byte identity:

   ```sh
   scripts/staging-equivalent-harness.sh validate-environment --config "$K_CONFIG"
   scripts/staging-equivalent-harness.sh validate-recovery \
     --config "$K_CONFIG" --output "$K_EVIDENCE_DIR/emergency-recovery-identity.env"
   ```

4. With explicit operator authorization for this isolated host only, invoke
   the repository-owned emergency path. It uses the same hermetic host PATH,
   revalidates the durable fence, and reads the canonical persisted R bytes:

   ```sh
   scripts/staging-equivalent-harness.sh rollback \
     --config "$K_CONFIG" --confirm-staging-equivalent
   ```

5. Run `attest-p` and preserve its output. If the exact R wrapper still cannot
   restore P, record `RECOVERY_RESULT=FAILED`, stop mutation attempts, and
   escalate with the evidence; do not improvise a candidate helper, branch/tag
   lookup, latest image, or host Node/npm workaround.

## Success leg

After a fault leg has restored and independently attested P, the success leg is
run separately and only on the isolated host:

```sh
scripts/staging-equivalent-harness.sh success-leg \
  --config "$K_CONFIG" --confirm-staging-equivalent
```

It repeats K0, captures P as `previous`, checks migration risk, preflights and
persists R before the boundary, streams the N→N+1 C entrypoint, and requires:

```text
PREPARED -> SWITCHING -> ACTIVATED_UNVERIFIED -> VERIFIED -> COMMITTED
current == C releaseId
previous == P releaseId
live digest pins == C
health == 200
ready JSON.ready == true
```

The success leg must also prove that `current` did not point to C during any
pre-commit phase.

## Evidence bundle

Each leg writes one bounded structured `evidence.json`, a generated human
summary, and an archive. The summary is derived from the JSON; it is not a
second source of truth. The archive includes the host contract/isolation
attestation, exact P/C/R identities, Release Bundle and RC IDs, OpenPath SHAs,
recovery hashes, migration classifier output, baseline and final container/
volume/mount snapshots, transaction history, phase observations, diagnostic
provenance, health/readiness results, pointers, and rollback outcome.

Evidence records and snapshots reject secret-shaped content and bounded lines.
They never include passwords, tokens, private keys, authorization headers, or a
complete `.env` file.

## Authorization boundary

This repository change authorizes no live operation. A later K execution needs
separate explicit authorization for the isolated host's provisioning and each
mutating leg. It must not mutate `PRODUCTION_RECOVERY_SHA`, GitHub environments,
GitHub secrets/variables, production hosts, production tags/releases, or issue
state. L, M, production deploy, production rollback, production tag, and
production release remain outside this runbook and require separate approval.
